`feature/Hu-06-tickets-sla`: todas las tareas quedan cerradas (`[x]`) con el criterio que
realmente se verificó. La spec está en `implementada` y el plan en `implementado`. No hay

siendo una integración pendiente); los comentarios viven en un repositorio en memoria.

- [x] **T1. Dominio del comentario y validación del contenido.** RF-62
  - Hecho cuando: `tickets/domain/entities.py` añade `TicketComment` (`id`, `ticket_id`, `author_id`, `body`, `created_at`), las constantes `COMMENT_MIN_LENGTH = 1` y `COMMENT_MAX_LENGTH = 2000`, y `validate_comment_body`, que reutiliza `_validate_text` (texto estricto, recorte `strip()`, límite en code points y valor recortado devuelto) sin duplicar la semántica de HU-02. `test_ticket_comments_domain.py` verifica el recorte, los límites exactos 1/2000 (incluido `"á" * 2000`), ocho valores inválidos (vacío, solo espacios, 2001, `None`, números, `bool`, listas, dict, bytes) y que la entidad solo tiene los cinco campos documentados.
- [x] **T2. Repositorio en memoria de comentarios.** RF-63
  - Hecho cuando: `tickets/infrastructure/ticket_comment_repository.py` implementa `InMemoryTicketCommentRepository` con `add`, `list_by_ticket`, `count`, `clear` y el singleton `get_ticket_comment_repository()`, siguiendo el patrón de `InMemoryTicketRepository`. `list_by_ticket` filtra por `ticket_id`, ordena por `created_at` ascendente y, al usar `sort` estable sobre el `dict` de inserción, conserva el orden de registro cuando hay empate. Se verifica el aislamiento entre tickets, el orden ascendente con fechas invertidas, el empate estable de tres comentarios y el estado vacío tras `clear`.

El orden deja 404 antes que 409 y no introduce códigos ni mensajes nuevos.
- [x] **T4. Casos de uso de creación y listado.** RF-61, RF-63, RF-67, RF-69
