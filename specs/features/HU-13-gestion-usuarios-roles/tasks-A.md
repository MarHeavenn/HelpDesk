# Lote A — Cuentas, invitaciones y roles

Dependencia: ninguna. Completar A antes de B. Estimación por tarea: 20–30 minutos. Tests primero; backend con `pytest` + `TestClient`, interfaz con Vitest/Testing Library. No crear pantallas de gestión.

- [x] **T1. Compatibilidad de cuenta y migración transaccional.** RF-105–RF-106, RF-118–RF-119, RF-123
  - Hecho cuando: pruebas cubren migración desde `001` e instalación limpia, `company_id` nullable, roles/estados e invariantes pending/hash y accepted/hash; todas las cuentas existentes quedan `accepted` conservando hash, rol, empresa y estado activo. Una migración fallida impide iniciar la aplicación y deja esquema y datos previos intactos; la migración nueva no modifica `001`.
- [x] **T2. Consulta, alta y unicidad de usuarios por tenant.** RF-105–RF-109, RF-117, RF-121
  - Hecho cuando: tests de aplicación y `TestClient` verifican lista/detalle propios, lista vacía y 404 uniforme ajeno/sin empresa; alta admin-only, empresa fijada por sesión, campos/cuerpo exactos, correo global único y conflicto genérico; rechazos no alteran datos ni exponen secretos. Pruebas registradas antes de implementar.
- [x] **T3. Edición, rol, estado y administrador activo.** RF-109–RF-112, RF-117, RF-121
  - Hecho cuando: tests comprueban PATCH parcial/null/vacío/extra, idempotencia, reenvío solo ante cambio de correo de cuenta pendiente, cambios de rol/estado, revocación e invariantes. Peticiones concurrentes atendidas por instancias/servidores distintos nunca dejan la empresa sin administrador activo; el conjunto coordinador se serializa con bloqueo transaccional PostgreSQL compartido, no con locks de proceso; errores respetan precedencias y no producen cambios parciales.
- [x] **T4. Ciclo de invitación, autenticación y estados SMTP.** RF-108, RF-118, RF-120–RF-121
  - Hecho cuando: `TestClient` verifica vínculo cuenta/empresa, 168 horas, rotación/un solo uso, aceptación y concurrencia entre instancias/servidores; prueba SMTP ausente=`not-attempted`, envío exitoso=`sent` y fallo configurado=`failed`. Las respuestas de alta, reenvío y PATCH con reenvío incluyen solo `{user,email_status}`, mantienen éxito HTTP, no incluyen `Invitation-Delivery`, y excluyen `email_status` de lista/detalle, otros PATCH y aceptación; se permite reintentar y no se filtran secretos.
  - Corrección ronda 2: el estado de cuenta/invitación se persiste en PostgreSQL (`003_identity_invitation_state.sql`) y aceptación, desactivación y rotación releen/mutan dentro de la misma transacción bloqueada; se añadieron pruebas con repositorios independientes.
- [x] **T5. Roles, guards y avisos en la interfaz existente; regresión A.** RF-105–RF-112, RF-117–RF-124
  - Hecho cuando: Vitest/Testing Library verifica cuatro roles, matriz de rutas permitidas/prohibidas de supervisor, rutas anidadas, navegación y ocultación de alta para técnico/supervisor. Para `failed` muestra literalmente «La cuenta y la invitación se crearon correctamente, pero hubo un problema al enviar el correo electrónico. Por favor, utiliza la opción de 'Reenviar invitación' desde el panel más tarde.»; para `not-attempted`, «No se pudo enviar el correo porque el servicio aún no está configurado». `pytest` + `TestClient`, pruebas frontend y build cubren A; se registran por RF resultados o brechas antes de habilitar B.
